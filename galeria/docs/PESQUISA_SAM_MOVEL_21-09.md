# Pesquisa: variantes do Segment Anything (SAM) para rodar no aparelho — 21/09/2026

## Contexto e critério de busca

App Android de edição de fotos em Kotlin. Runtime: ONNX Runtime 1.30 ou TensorFlow Lite. Hardware alvo: CPU arm64, **sem GPU/NPU delegate garantido** (tem que funcionar em CPU pura no pior caso). O app já tem recorte automático de pessoa (ISNet + ML Kit Subject Segmentation); o SAM entraria para o gesto "tocar num objeto para selecionar" (prompt de ponto ou caixa), não para recorte automático de pessoa.

Metodologia: 5 pesquisas paralelas via WebSearch + WebFetch, mais 3 verificações diretas de fontes primárias feitas depois para resolver divergências entre as pesquisas. Datas de commit do GitHub confirmadas via API do GitHub quando indicado. Toda afirmação abaixo tem URL; onde não achei dado confiável, está escrito **não encontrado** em vez de estimado.

## Resumo executivo

### (a) Qual escolher para caber em 46 MB ou menos de download

**EfficientSAM-Ti** (Meta, `yformer/EfficientSAM`) é o candidato que cabe com folga: export ONNX oficial com encoder (24,8 MB) + decoder (16,6 MB) = **41,4 MB fp32**, Apache 2.0 em código e pesos, licença sem restrição de uso comercial ([LICENSE](https://raw.githubusercontent.com/yformer/EfficientSAM/main/LICENSE), [HF Space oficial](https://huggingface.co/spaces/yunyangx/EfficientSAM/tree/main)). Existe ainda uma versão int8 fundida (encoder+decoder num grafo só) de **20,5 MB** via OpenCV Zoo ([HF opencv/image_segmentation_efficientsam](https://huggingface.co/opencv/image_segmentation_efficientsam/tree/main)), mas não consegui confirmar se essa versão fundida preserva a arquitetura "encoder 1x + decoder por clique" ou se reprocessa a imagem inteira a cada toque — **não encontrado**, precisa testar antes de adotar.

O concorrente óbvio, **MobileSAM**, quase cabe mas passa do teto: o único par oficial de tamanhos vindo de uma fonte única e consistente (Qualcomm AI Hub) é encoder 26,6 MB + decoder 23,7 MB = **50,3 MB fp32** ([huggingface.co/qualcomm/MobileSam](https://huggingface.co/qualcomm/MobileSam), confirmado por fetch direto na página). Existe uma cifra concorrente de 40,7 MB para o `.pt` combinado ([Ultralytics](https://docs.ultralytics.com/models/mobile-sam/)), mas esse é o checkpoint PyTorch, não o par ONNX que de fato roda no ONNX Runtime Mobile — para a decisão de orçamento de download, o número que importa é o ONNX (50,3 MB), que estoura os 46 MB.

Conclusão: **EfficientSAM-Ti** para o orçamento de 46 MB; MobileSAM como alternativa aceitável se o teto for flexibilizado para ~50 MB (mIoU muito parecido, ecossistema de exemplos mais maduro — ver tabela).

### (b) Riscos

1. **Licença** — dois riscos concretos apareceram:
   - **EdgeSAM é NTU S-Lab License 1.0, explicitamente não-comercial** ("Redistribution and use for non-commercial purpose... are permitted") ([LICENSE](https://github.com/chongzhou96/EdgeSAM/blob/master/LICENSE)). Não encontrei canal de licenciamento comercial declarado no repositório. Isso desqualifica o EdgeSAM para um produto pago, independente da qualidade técnica.
   - **SAM 3 (lançado 19/11/2025, Meta) não é Apache 2.0** — usa uma "SAM License" própria que permite uso comercial mas proíbe engenharia reversa e uso militar/ITAR/nuclear/espionagem, e os pesos são gated (formulário de acesso) ([LICENSE](https://huggingface.co/facebook/sam3/blob/main/LICENSE), [repo](https://github.com/facebookresearch/sam3)). Não bloqueia um editor de fotos, mas é uma ruptura de padrão em relação ao SAM 1/2 (Apache 2.0) que vale registrar — e é moot de qualquer forma porque o SAM 3 tem ~900M parâmetros, inviável em CPU de celular (ver item SAM 3 na tabela).
   - Todos os outros modelos pesquisados (MobileSAM, TinySAM, EfficientSAM, NanoSAM, SlimSAM, EfficientViT-SAM, RepViT-SAM, SAM2/2.1, EdgeTAM) são Apache 2.0 em código; a licença dos pesos especificamente nem sempre tem uma declaração textual separada — na maioria dos casos é razoável inferir que segue o código (mesmo repositório), mas isso é inferência, não citação direta, e está marcado como tal em cada ficha abaixo.
   - O dataset SA-1B (usado para treinar o SAM original) é restrito a pesquisa, mas isso **não** impede uso comercial dos pesos já treinados — a própria Meta declara isso ([ai.meta.com/datasets/segment-anything](https://ai.meta.com/datasets/segment-anything/)).

2. **Memória em entrada 1024x1024** — não encontrei número de RAM/OOM específico de Android via ONNX Runtime Mobile ou TFLite para nenhum dos modelos. A melhor evidência indireta que apareceu: o próprio README oficial do RepViT-SAM relata que, no benchmark de CoreML em iPhone 12, **os encoders do MobileSAM e do ViT-B-SAM deram OOM (estouro de memória)** no mesmo aparelho e resolução (1024x1024), enquanto o encoder CNN do RepViT-SAM (mais leve) rodou sem problema ([RepViT/sam/README.md](https://github.com/THU-MIG/RepViT/blob/main/sam/README.md)). É iOS/CoreML, não Android, mas é evidência real de que encoders ViT em 1024x1024 estouram memória num aparelho de gama média de ~2020 — tratar como risco real, não hipotético, para qualquer variante com encoder ViT (MobileSAM, TinySAM, EfficientSAM-S, EfficientViT-SAM) rodando em aparelhos com pouca RAM.

3. **Tempo do encoder em CPU pura** — este é o achado mais importante da pesquisa. Os números de latência "bons" que apareceram (EdgeTAM 8-14 ms, SAM2.1 quantizado 34 ms, ambos via Qualcomm AI Hub) **não são CPU pura** — verifiquei diretamente na página da Qualcomm e o "Primary Compute Unit" declarado para esses benchmarks é **NPU**, não CPU ([huggingface.co/qualcomm/EdgeTAM](https://huggingface.co/qualcomm/EdgeTAM), confirmado por fetch direto). Como o projeto exige funcionar **sem GPU/NPU delegate garantido**, esses números não são representativos do pior caso.
   Os únicos dois números que encontrei de CPU-only real em celular apontam para segundos, não milissegundos: EdgeSAM em CPU (ONNX, execution provider CPU) levou **3.000-4.000 ms por imagem** num Samsung A20 (chip Exynos 7884, entrada de 2019) — e isso a 720x540, resolução menor que 1024x1024, então o pior caso real é pior ainda ([issue #18 do EdgeSAM](https://github.com/chongzhou96/EdgeSAM/issues/18)). O paper do SqueezeSAM cita o SAM completo (ViT-H) levando "mais de dez segundos" num CPU de iPhone, contra meio segundo numa GPU A100 ([arXiv:2312.06736v2](https://arxiv.org/html/2312.06736v2)). Nenhuma fonte confirma tempo de encoder abaixo de 1-2 segundos em CPU pura de celular real, para nenhum dos modelos pesquisados. **Tratar isso como risco real de UX**: "tocar e esperar a seleção aparecer" pode facilmente passar de 1-3 segundos em aparelhos de entrada/intermediários sem delegate, mesmo com um modelo pequeno.

### (c) SAM substitui ou só complementa o recorte tipo ISNet/remove.bg em borda de cabelo e alfa

**Só complementa — não substitui.** Três evidências:

1. O SAM (qualquer versão) produz **máscara binária/dura**, não um alpha matte nativo com transparência gradual. Isso é reconhecido na própria comunidade de pesquisa: o paper "Segment Anything in High Quality" (HQ-SAM) existe especificamente para corrigir "bordas de máscara grosseiras" do SAM original ([arXiv:2306.01567](https://arxiv.org/abs/2306.01567)). O paper Matte Anything é direto: "ao contrário da segmentação de imagem, o matting de imagem natural oferece previsões mais precisas e se destaca em lidar com objetos transparentes" ([huggingface.co/papers/2306.04121](https://huggingface.co/papers/2306.04121)).

2. O padrão de integração que a literatura de fato usa é **SAM localiza, uma rede de matting refina a borda** — não o SAM sozinho. O projeto Matte Anything usa o clique do usuário + SAM só para gerar um "pseudo-trimap", que depois é processado pela rede ViTMatte para produzir o alfa final ([hustvl/Matte-Anything](https://github.com/hustvl/Matte-Anything), MIT). Existe até um modelo de pesquisa mais recente unificando os dois estágios ("Segment and Matte Anything in a Unified Model", [arXiv:2601.12147](https://arxiv.org/abs/2601.12147)), o que reforça que a comunidade trata como dois problemas que precisam ser resolvidos juntos, não um substituindo o outro.

3. Não encontrei nenhuma métrica numérica publicada isolando fio de cabelo especificamente (nem para SAM, nem para ISNet, nem comparando os dois) — **não encontrado** um SAD ou mIoU de borda de cabelo. As comparações que existem são qualitativas: um benchmark da Photoroom (concorrente comercial, viés esperado a favor do próprio produto) e uma review independente que descreve a borda do SAM como "fuzzy" e que "pode sobrepor ou cortar partes" ([docs.photoroom.com](https://docs.photoroom.com/resources/remove-background-competitors-benchmark-remove.bg-clipdrop-sam-azure), [delesign.com](https://www.delesign.com/blog/removal-ai-vs-segment-anything-background-removal-via-ai)).

Conclusão prática para o app: use o SAM para responder "quais pixels, aproximadamente, pertencem ao objeto tocado" (seleção/localização por prompt de ponto/caixa). Para objetos de borda dura (garrafa, capacete, placa) a máscara do SAM pode bastar sozinha. Para cabelo, pelo ou borda semi-transparente, o pipeline correto é SAM seleciona a região aproximada e o ISNet (ou um estágio de matting equivalente) roda em cima, exatamente como a arquitetura Matte Anything já demonstra.

## Fichas por modelo

### MobileSAM (`ChaoningZhang/MobileSAM`)
1. Licença código: Apache 2.0 — [LICENSE](https://github.com/ChaoningZhang/MobileSAM/blob/master/LICENSE). Licença pesos: mesmo repositório, sem declaração separada — inferência, não citação direta.
2. Pesos: encoder (TinyViT) fp32 = 26,6 MB, decoder fp32 = 23,7 MB, confirmado por fetch direto na página oficial ([Qualcomm AI Hub](https://huggingface.co/qualcomm/MobileSam)). Checkpoint `.pt` combinado = 40,7 MB, 9,66M parâmetros ([Ultralytics](https://docs.ultralytics.com/models/mobile-sam/)) — ver nota de divergência acima. Quantizado: não encontrado tamanho oficial. Export ONNX oficial via `scripts/export_onnx_model.py` no próprio repo ([DeepWiki](https://deepwiki.com/ChaoningZhang/MobileSAM/3.4-onnx-export), [issue #20](https://github.com/ChaoningZhang/MobileSAM/issues/20)); comunidade: [awarebayes/MobileSamONNX](https://github.com/awarebayes/MobileSamONNX), [vietanhdev/samexporter](https://github.com/vietanhdev/samexporter), [Acly/MobileSAM no HF](https://huggingface.co/Acly/MobileSAM). TFLite oficial: não encontrado.
3. Latência: não encontrado em celular real. Únicos números achados são desktop: 23.802 ms/imagem em CPU de um Apple M4 (não otimizado), e "8 ms encoder + 4 ms decoder" sem hardware especificado (provavelmente GPU de notebook) ([Ultralytics](https://docs.ultralytics.com/models/mobile-sam/)).
4. Qualidade: mIoU ~0,74 (fonte secundária, ~2-4 pontos abaixo do SAM original), acurácia do encoder 72,8% no COCO ([EmergentMind](https://www.emergentmind.com/topics/mobilesam)) — a tabela original do paper ([arXiv:2306.14289](https://arxiv.org/pdf/2306.14289)) não foi extraída com confiança suficiente para citar o número oficial exato.
5. Resolução: não encontrada citação textual direta; 1024x1024 é esperado por herdar o mask decoder original do SAM, mas isso é inferência de compatibilidade. Arquitetura encoder-1x/decoder-por-clique confirmada pela existência de arquivos ONNX separados.
6. Android: [shubham0204/Segment-Anything-Android](https://github.com/shubham0204/Segment-Anything-Android) — Kotlin puro (confirmado via API do GitHub), ORT Mobile, último commit 2025-02-01, documenta SAM/SAM2 mas não testa MobileSAM explicitamente. [slz929/mobileSAM-Android-MNN](https://github.com/slz929/mobileSAM-Android-MNN) existe mas é C++/MNN (não Kotlin/ORT/TFLite), último commit 2023-12-05 — não atende ao requisito de stack. Repositório oficial ativo: último push em 2026-05-05 (API do GitHub).

### TinySAM (`xinghaochen/TinySAM`, AAAI 2025)
1. Licença: Apache 2.0, código e pesos (mesmo repositório/organização) — [LICENSE](https://github.com/xinghaochen/TinySAM/blob/main/LICENSE), [HF](https://huggingface.co/xinghaochen/tinysam).
2. Pesos: `tinysam.pth` = 40,7 MB, arquivo único sem separação oficial de encoder/decoder ([HF](https://huggingface.co/xinghaochen/tinysam/tree/main)). Existe Q-TinySAM (W8A8, quantização pós-treino) mas tamanho exato não encontrado ([HF](https://huggingface.co/xinghaochen/Q-TinySAM)). Export ONNX/TFLite oficial: não encontrado — nem no GitHub nem no HF; o `samexporter` não lista TinySAM entre os suportados.
3. Latência: só GPU — T4: TinySAM 38,4 ms, Q-TinySAM 24,0 ms, SAM-H 2.392 ms; V100 modo "everything" 0,93 s ([arXiv:2312.13789](https://arxiv.org/html/2312.13789)). Não encontrado em celular.
4. Qualidade (AP zero-shot instance segmentation): COCO — SAM-H 46,6% vs TinySAM 42,3% vs Q-TinySAM 41,4%; LVIS — SAM-H 44,7% vs TinySAM 38,9% vs Q-TinySAM 38,5% ([arXiv:2312.13789](https://arxiv.org/html/2312.13789)).
5. Resolução: 1024x1024 citado nas comparações de latência ([arXiv:2312.13789](https://arxiv.org/html/2312.13789)). Arquitetura encoder-1x confirmada textualmente ("image embeddings... computed and stored in advance").
6. Android: não encontrado, coerente com a ausência de export ONNX/TFLite.

### EdgeSAM (`chongzhou96/EdgeSAM`)
1. Licença: **NTU S-Lab License 1.0, explicitamente não-comercial** — "Redistribution and use for non-commercial purpose... are permitted" ([LICENSE](https://github.com/chongzhou96/EdgeSAM/blob/master/LICENSE)). Sem canal de licenciamento comercial declarado no README.
2. Pesos: tamanho em MB não encontrado (o model zoo do README lista formatos e mAP, não tamanho). Uma cifra de "164,3M parâmetros" extraída do paper é suspeita/incompatível com o porte "edge" do modelo — tratada com cautela, não confirmada ([arXiv:2312.06660v2](https://arxiv.org/html/2312.06660v2)). Variantes EdgeSAM, EdgeSAM-3x, EdgeSAM-10x (só PyTorch, resto "TBA"). Export ONNX oficial (encoder/decoder separados) e CoreML oficial confirmados; TFLite não mencionado.
3. Latência: encoder CNN 26 ms/imagem → 38,7 FPS no **iPhone 14** via CoreML/Neural Engine (não CPU pura, não Android) ([arXiv:2312.06660v2](https://arxiv.org/html/2312.06660v2)). Em **CPU real** (ONNX, execution provider CPU) num Samsung A20 (Exynos 7884): **3.000-4.000 ms por imagem a 720x540** — a resolução é menor que 1024x1024, então o pior caso real tende a ser pior ([issue #18](https://github.com/chongzhou96/EdgeSAM/issues/18)).
4. Qualidade (mIoU, box prompt de GT): COCO EdgeSAM 76,7 vs SAM 77,3; LVIS EdgeSAM 76,2 vs SAM 77,8. Com 2 cliques de refinamento adicionais, EdgeSAM chega a superar o SAM (79,0 vs 78,1 COCO; 78,0 vs 78,5 LVIS) ([arXiv:2312.06660v2, Tabela 2](https://arxiv.org/html/2312.06660v2)). AP zero-shot: 42,1 mAP COCO.
5. Resolução: confirmado explicitamente "(3,1024,1024)" ([arXiv:2312.06660v2](https://arxiv.org/html/2312.06660v2)). Encoder é CNN (não ViT), roda 1x; decoder por prompt.
6. Android: não encontrado. Existe app iOS em produção ("CutCha", [App Store](https://apps.apple.com/us/app/cutcha-photo/id6478521132)), mas iOS/CoreML, não Android.

## Lacunas consolidadas ("não encontrado")

- Latência medida em celular Android real, em CPU pura (sem NPU/GPU delegate), para praticamente todos os modelos — a única exceção é o dado pontual de EdgeSAM no Samsung A20 (3-4 s) e a alegação genérica do SqueezeSAM sobre CPU de iPhone (SAM completo, >10 s).
- Tamanho de pesos quantizados (int8/fp16) para a maioria dos modelos — só EfficientSAM-Ti (int8, OpenCV Zoo, 20,5 MB) tem número confirmado.
- Export TFLite oficial — não encontrado para nenhum dos 11 modelos pesquisados (só ONNX e, em alguns casos, CoreML/TensorRT).
- mIoU vs SAM ViT-H isolado para: TinySAM (só AP), NanoSAM, RepViT-SAM (só AP), SAM2.1-hiera-tiny especificamente (só SAM2 geral), EdgeTAM (só vs SAM2.1-B+), SlimSAM variante "uniform" especificamente.
- Repositório Android Kotlin/Java dedicado e testado para: TinySAM, EdgeSAM, EfficientSAM, NanoSAM, SlimSAM, EfficientViT-SAM, RepViT-SAM, EdgeTAM, SAM3. Só MobileSAM e SAM2/2.1 têm um repositório Android genérico que roda ([shubham0204/Segment-Anything-Android](https://github.com/shubham0204/Segment-Anything-Android)), sem confirmação de teste específico por variante além do SAM/SAM2 original.
- Resolução de entrada declarada explicitamente (em vez de inferida por arquitetura) para: MobileSAM, EfficientSAM, SlimSAM.
- Número de RAM/OOM específico de Android via ONNX Runtime Mobile ou TFLite, para qualquer modelo — a melhor evidência disponível é o relato de OOM do RepViT-SAM sobre MobileSAM/ViT-B-SAM em iPhone 12 (iOS, não Android).
